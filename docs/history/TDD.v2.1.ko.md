**현재 제품의 검증 범위는 21~26장과 SDD 20~29장을 우선한다.** 1~20장은 기존 코드 특성화와 이전 개선안의 기록이다. 기존 영화 장르·평점·개봉일·외부 카탈로그 테스트를 신규 제품의 필수 조건으로 자동 승계하지 않는다. 인증·DTO·접근성·캐시 격리·실제 재생 관련 원칙은 적용 범위에 맞게 이어받는다. 신규 사례는 전부 목표·미실행이며, 문서 갱신을 구현 또는 테스트 통과로 취급하지 않는다.

버전 1.1은 Fakeflix `2ef25d14a112e3c90e4b482b4c964b9404d436b6` 분석을 바탕으로 SDD 9~14장의 목표 설계를 검증하는 13~16장을 추가한다. 기존 사례의 ‘현재’ 판정은 원본 NextFlix에만 적용한다. 신규 사례는 모두 목표·미실행이며 Fakeflix를 실행해 검증한 결과가 아니다. 기술 스택과 애플리케이션 소스는 변경하지 않았다.

버전 1.2는 karlhadwen/netflix `54ead17f6b8a240b4ab0d2eeff9d1c66c0a6c206`의 코드와 테스트를 참고해 17~20장을 추가한다. 이전 테스트 ID와 기준을 보존하며, 모달 지연의 변경 목표는 DLG-03이 UI-01을 보완한다. 신규 사례 역시 모두 목표·미실행이다.

## 1 검증 원칙

정상 구현을 확인하는 사례와 개선 요구사항을 확인하는 사례를 구분한다. 표의 ‘현재’는 기존 동작에 대한 검증, ‘목표’는 수정 이후 충족할 계약이다. 목표 사례가 기존 코드에서 실패할 것으로 예상되어도 실행 결과 없이 실패로 보고하지 않는다. 기존의 해시 반환이나 잘못된 상태 코드를 제품 합격 조건으로 고정하지 않는다.

현재 구현의 검증 범위는 Credentials·OAuth 인증, 계정 조회, 전체·단일·무작위 영화 조회, 찜 추가·삭제·조회, 상세 모달, 영상 재생 및 반응형 화면이다. 버전 1.1 목표 범위에 제목 검색·장르 탐색·추가 로딩·My List 독립 화면을 포함한다. 결제·추천·다중 프로필·인물 검색·자체 영상 인코딩은 합격 대상에서 제외한다.

## 2 테스트 계층과 환경

| 계층 | 검증 대상 | 격리 방법 | 제안 도구 |
| --- | --- | --- | --- |
| 단위 | Zustand 상태, 서버 인증 분기, 입력·오류 변환 | getServerSession·Prisma·시간·난수 대체 | Vitest 또는 Jest 중 프로젝트에서 하나 선택 |
| 컴포넌트 | 로그인 폼, 찜 버튼, 모달, 로딩·오류 화면 | SWR 캐시를 사례별 초기화, API 응답 대체 | React Testing Library 및 MSW |
| API 통합 | HTTP 상태·헤더·본문, 세션, Prisma 쿼리 | 실제 Next 서버와 전용 MongoDB, 테스트 계정 | HTTP 클라이언트와 테스트 runner |
| E2E | 가입부터 재생·로그아웃까지 | 전용 서버·계정·미디어 fixture | Playwright |
| 운영 특성 | 접근성, 동시성, 지연, 배포 smoke | 브라우저·부하 환경 및 결과 증거 | 접근성 검사 도구와 부하 생성기 |

이 도구들은 도입 제안이며 현재 저장소 의존성으로 설치된 상태가 아니다. 서버 세션을 mock하는 단위 테스트만으로 실제 쿠키·JWT·OAuth 흐름이 검증되었다고 간주하지 않는다.

테스트 환경은 동일한 lockfile로 설치하고 실제 설치 버전, Node 버전, OS, 브라우저 버전을 결과에 남긴다. MongoDB는 Prisma 사용에 필요한 구성을 갖춘 격리 환경을 준비한다. 운영 DB나 실제 사용자 계정은 사용하지 않는다. OAuth는 별도의 테스트 앱·callback URL·계정을 사용하며 정상 경로 외에 취소와 실패를 수동 또는 통제된 통합 환경에서 검증한다.

서버 실행 준비 순서는 의존성 설치, Prisma Client 생성, 전용 DB 스키마 적용, fixture 적재, 환경변수 설정, 서버 기동이다. MongoDB용 스키마 적용 절차를 별도로 확인하고 README의 migrate 명령을 무조건 실행하지 않는다. 현재 없는 test 스크립트가 실행 가능하다고 가정하지 않는다.

## 3 테스트 데이터

| 데이터 | 구성과 용도 |
| --- | --- |
| U1 | Credentials 사용자. 유효 해시, favoritesIds 빈 배열 |

| M2 | ID `000000000000000000000002`, 별도 정상 영화 |
| X1 | ID `000000000000000000000099`, DB에 존재하지 않는 유효 ObjectId |

영화는 [스키마](https://github.com/LucasDaSilva96/NextFlix/blob/5b67a0227640b95d8fd115b71c55f84a5cadbdf3/prisma/schema.prisma)의 필수 필드를 모두 채운다. 비밀번호는 테스트 전용 생성값을 사용하고 저장값은 평문과 다르며 bcrypt 비교가 성공하는지 확인한다. 테스트 데이터의 이메일은 예를 들어 `u1@example.test`를 사용한다. 각 사례는 초기 찜 배열을 명시하고 종료 후 fixture를 복원한다. 병렬 실행은 별도 DB 또는 고유 실행 ID로 충돌을 방지한다.

## 4 인증과 등록 테스트

P0는 배포 차단, P1은 핵심 기능·데이터 정확성, P2는 사용성·운영 품질이다. 실행 수준의 U는 단위, C는 컴포넌트, I는 통합, E는 E2E이다.

| --- | --- | --- | --- |
| REG-01 | 현재 P1 I | 미등록 이메일로 name/email/password POST | 201, User 1개 생성, 평문 비밀번호 미저장, bcrypt 비교 성공. 응답 필드 안전성은 SEC-01에서 별도 판정 |

| REG-03 | 목표 P1 I | 필드 누락·빈 문자열·공백·잘못된 타입·깨진 JSON을 각각 전송 | 검증 오류 400, DB 쓰기 없음. 길이와 비밀번호 경계값은 정책 확정 후 추가 |
| REG-04 | 목표 P1 I | 같은 이메일로 동시 가입 2회 | 생성은 1건, 성공 201과 충돌 409로 구분. 미인증 이메일은 emailVerified null |

| AUTH-02 | 현재 P1 U/I | 잘못된 비밀번호·없는 이메일·누락 자격 증명·U3의 Credentials 로그인 각각 시도 | 로그인 거절, 인증 세션 생성 없음. 반환 오류 메시지의 정보 노출은 별도 개선 대상 |
| AUTH-03 | 현재 P1 I/E | GitHub·Google 각각 성공, 취소, callback 오류 | 성공 시 계정 연결과 `/profiles` 이동. 취소·오류 시 보호 데이터 접근 불가 |
| AUTH-04 | 목표 P1 I | 쿠키 없음·손상·만료, 삭제된 User 세션으로 각 보호 API 호출 | 401과 일관된 오류 객체. 서버 내부 정보와 User 데이터 미반환 |
| AUTH-05 | 현재 P1 E | 로그인 후 메뉴 로그아웃, 보호 페이지·API 재접근 | 세션이 제거되고 `/profiles`는 `/auth` 이동. 보호 API는 거절. 현재 API 오류 코드는 SDD와 비교 |

AUTH-03은 제공자별 테스트 앱 준비가 진입 조건이다. 준비되지 않으면 ‘환경 차단’으로 기록하며 단위 테스트 성공으로 대체하지 않는다. AUTH-04는 current, movies, movies/id, random, favorite의 모든 메서드를 순회한다. `movies/undefined`도 포함한다.

| PLAY-02 | 목표 P1 E | 영상 404·지원 안 되는 코덱·자동재생 제한 | 영상 실패 또는 수동 재생 안내 제공. 브라우저 자동재생 차단을 앱 성공으로 오판하지 않음 |
| A11Y-01 | 목표 P2 E | 키보드만으로 로그인·프로필·상세·찜·모달 종료 수행 | 조작 요소의 이름과 초점 표시, 모달 focus trap·Escape 종료·트리거로 초점 복귀 |

실제 재생은 태그 존재만으로 판정하지 않는다. 통제된 호환 영상에서 `loadeddata` 또는 준비 상태와 재생 후 `currentTime` 증가를 확인한다. 외부 제공 URL은 별도 smoke 테스트로 구분해 외부 네트워크 장애가 결정적 회귀 테스트를 흔들지 않게 한다.

## 7 보안과 성능 테스트

| ID | 기준·우선·수준 | 절차 | 합격 기준 |
| --- | --- | --- | --- |
| SEC-01 | 목표 P0 I | 등록·current·찜 POST/DELETE 응답을 Credentials 사용자로 검사 | hashedPassword·password·access_token·refresh_token 필드가 응답 어디에도 없음. 빈 문자열 마스킹도 DTO 제거 목표에는 불합격 |
| SEC-02 | 목표 P1 빌드/E | 데모 설정 포함 production bundle과 데모 계정 권한 검사 | 비공개 자격 증명 없음. 공개 데모 정보가 있다면 공개 전용 계정·데이터 격리 정책 충족 |

SEC-03은 현재 코드에 CSRF 취약점이 확정되었다는 뜻이 아니다. 브라우저 쿠키·Origin·요청 형식이 결합된 동작을 검증하는 항목이다. 부하 시험은 운영 서비스에 실행하지 않고 시험 시간·준비 단계·데이터 크기를 결과에 함께 기록한다.

## 9 테스트 주도 개선 절차

1. SEC-01에서 등록 및 찜 응답의 민감 필드 부재를 검사하는 테스트를 먼저 작성하여 기존 구현의 실패를 확인한다.
2. 서버의 공통 응답 DTO를 적용한 후 등록·찜·current 테스트를 통과시킨다.
3. MOV-03·04를 작성하고 ID 파싱·조건부 SWR 요청을 수정한다.
4. FAV-03·04로 중복과 갱신 손실을 재현한 후 DB 원자적 연산 또는 고유 제약을 적용한다.
5. API-01·AUTH-04로 오류 계약을 통일하고 실제 세션 통합 테스트를 수행한다.
6. 각 변경마다 관련 컴포넌트·API·E2E 회귀를 실행하고 리팩터링 후 같은 검증을 유지한다.

위 절차는 실행 계획이다. 이 문서 작성 과정에서 테스트 코드를 추가하거나 애플리케이션 결함을 수정하지 않았다.

## 10 진입 조건과 종료 조건

진입 조건은 전용 DB·fixture·환경변수·테스트 실행 도구·애플리케이션 기동이 준비되고, 테스트별 현재 계약 또는 목표 계약을 선택한 상태이다. OAuth·실제 미디어·부하는 별도 환경 진입 조건을 둔다.

배포 종료 조건은 P0 미해결 0건, 핵심 P1 사례 전부 통과, E2E-01 성공, 제공자별 인증 통합 검증 완료, 보안 응답 검사 성공이다. 실행하지 못한 항목은 성공으로 계산하지 않는다. P2 잔여 항목은 영향과 보완 일정을 기록한다. 개선 정책 미확정 항목은 책임자가 수용 기준을 확정하기 전까지 조건부 상태로 유지한다.

자동화 도입 후 PR 검증에는 lint·타입 확인·단위·컴포넌트·API 통합을 포함하고, 배포 후보에는 build·E2E·OAuth smoke를 추가한다. 전체 커버리지 숫자보다 인증 허용/거절, 오류 계약, 찜 중복·동시성 및 민감 필드 누락 분기를 우선한다.

## 13 Fakeflix 참고 설계의 추가 테스트

새 사례의 기술 전제는 기존 Next.js API·NextAuth·SWR·Zustand·Prisma·MongoDB이다. Redux·Firebase·Swiper·Framer Motion이 설치되었는지를 합격 조건으로 사용하지 않는다. Fakeflix 코드 근거와 채택 판단은 [SDD 9장 및 14장](SDD.v2.1.ko.md)에 정리했다.

### 13.1 추가 데이터와 환경

서로 다른 ObjectId를 가진 영화 55개를 만들어 장르 A 30개·장르 B 25개로 나눈다. ID 정렬 결과를 fixture의 기대 배열로 저장한다. 같은 제목·다른 ID, 한글·영문 혼합 제목, `&`, `+`, `?`, 정규식 메타문자, 결합문자 제목을 추가 검색 fixture로 둔다. 검색 경계는 0·1·100·101 Unicode 코드 포인트를 사용한다. 추가 메타데이터는 null, 평점 0, 유효 평점, 잘못된 척도, 미상 연령 정보를 준비한다.

목록 지연·역순 응답·추가 페이지 실패·401을 네트워크 계층에서 주입한다. 기존 회원 U1·U2의 별도 세션, 계정 전환 직전에 완료되지 않은 요청, 별도 브라우저 컨텍스트를 준비한다. DB 이행 fixture에는 중복 찜·유효 찜·삭제된 영화 ID·빈 배열을 포함한다.

## 15 단계별 승인 기준과 테스트 주도 순서

1. 단계 A는 기존 SEC-01·AUTH-04·API-01·MOV-04와 MIG·FAV 경쟁 테스트를 먼저 작성한다. 실제 세션·DB 통합 검증이 끝나야 신규 탐색 기능을 배포한다.
2. 단계 B는 SRCH-04·PAGE-01·PAGE-03·LIST-02처럼 경쟁·실패 사례를 먼저 재현하고 catalog와 화면을 구현한다. COMPAT-01·02와 E2E-03·04를 함께 실행한다.
3. 단계 C는 UX·META 사례 및 접근성·재생 회귀를 완료한다. 키보드로 핵심 경로가 불가능하면 해당 릴리스의 차단 결함으로 취급한다.
4. 단계 D는 이번 통과율 계산에서 제외한다. 추후 외부 제공자·시리즈를 채택하면 외부 ID 충돌, 429·타임아웃, 비밀키 미노출, 재생 불가 콘텐츠 표시에 대한 별도 계약과 테스트를 추가한다.

각 단계는 해당 P0·P1 전부 통과하고 기존 단계의 회귀가 없어야 완료로 본다. 문서의 ‘목표’는 구현·실행 증거가 생기기 전까지 미실행 상태를 유지한다. 새 테스트를 추가하면서 NextFlix 런타임을 Redux·Firebase·React Router로 교체하지 않는다.

## 16 이번 갱신의 검증 상태

Fakeflix 소스와 두 저장소의 구조를 비교하고 기능 채택·보류·제외 사유를 기록했다. 신규 테스트는 구현 전 설계이며 자동화 스크립트, 의존성 설치, DB 이행, 외부 서비스 연동, 브라우저 실행은 수행하지 않았다. 기존 결과 기록 양식에 신규 ID를 그대로 사용한다.

## 20 자동화와 완료 기준 보완

2장의 runner 선택지는 구현 착수 시 하나로 확정한다. 이번 권장안은 Next.js 연동 Jest와 React Testing Library, 실제 DB API 통합, Playwright E2E 조합이다. 이는 개발·검증 도구 제안이며 현재 package.json에 설치되거나 스크립트가 추가된 상태가 아니다. 참고 저장소의 CRA·watchAll 명령을 복사하지 않고 CI에서는 종료 가능한 단발 실행을 구성한다.

수집 범위에는 인증 옵션·serverAuth·입력/복귀 검증·catalog cursor·Favorite 서비스와 관련 hooks를 포함한다. 생성 파일·정적 자산 제외는 명시하되 위험한 코드를 단순히 제외해 커버리지 숫자를 높이지 않는다. 90% 수치를 바로 목표로 고정하지 않고 초기 측정 후 변경 코드의 미검증 중요 분기를 검토한다. P0·P1 행위 사례 통과와 실제 세션·DB 증거는 커버리지와 별개의 필수 조건이다.

단계 A 완료에 FORM·NAV·DATA를, 단계 C 완료에 DLG·COMP·PLAY 추가 사례를 포함한다. 모든 P0·P1은 통과해야 하며 실제 브라우저 영상·초점·OAuth 확인을 jsdom 성공으로 대체하지 않는다. 신규 문서 작성 시점에는 소스·테스트 정적 분석만 완료했고 참조 저장소 및 NextFlix 테스트 실행은 수행하지 않았다.

## 21 제품 검증 범위와 협의 상태

Windows PC + 공용 NAS/SMB, 팀 약 10명·원본 약 10TB, 방송연도 기준, 종류·담당자·제작부조·UE 버전·방송 제목·키워드를 확인했다. 후속 답변으로 UE 5.3/5.4/5.6/5.8, Launcher/UE 호환 커스텀 엔진, Blueprint 중심·일부 C++, Actor Sequence 등, **기존 제작 프로젝트에 에셋·의존성 추가**, 제작부조 `TS-1~TS-D`·홀·중계차를 확정 반영했다. 신규 ARC/ANF 요구는 SDD 20~29장과 연결한다. 엔진 build·추가 플러그인·TS 개별 목록·파일 수/구조는 미확정이다.

신규 테스트 수준은 U(단위), I(실제 API/DB/파일시스템/worker 통합), E(브라우저·업무 E2E), UE(실제 엔진)이다. 중요도 B0는 원본 훼손·권한 노출·잘못된 대상 변경 차단, B1은 핵심 업무, B2는 보조 품질이다. SDD 단계 P0~P4와 중요도 표기를 구분한다. mock 성공만으로 SMB·권한·엔진 결과를 통과시키지 않는다.

실제 NAS·방송 원본·운영 프로젝트에 실패를 주입하지 않는다. 전용 공유·격리 DB·테스트 UE 프로젝트·승인 대상 루트에서 검증한다. 원본 파일 불변은 별도 fixture의 전후 해시·크기·mtime와 파일 생성/삭제 감시로 확인하고 10TB 전수 해시로 대체하지 않는다.

**ARC-E2E-01 / B1:** 관리자의 전용 공유 등록→dry-run→후보 확인→편집자 영상/프로젝트/에셋 연결·필수 정보 입력→연도 홈→방송 제목/키워드 검색→상세·썸네일·실제 프리뷰→에셋 역탐색→원본 위치 복사→재조사. 동일 ID·관계·연도·대표 버전·수동 정보가 유지되어야 한다.

**ARC-E2E-02 / B0:** 제한 사용자가 공유 에셋에서 숨긴 프로젝트·미디어·경로 접근→거절→계정 전환 중 이전 응답 도착→노출 없음. SMB 단절 후 상세 확인→원본 연결 불가 안내→복귀·재조사로 복원, 카탈로그 자동 삭제 없음.

## 25 테스트 주도 순서·릴리스 기준

1. P0: 미결정 질문·버전별 지원표·전용 SMB/UE fixture·원본 감시·판정 기준을 준비한다. 실제 사용 엔진 spike로 무인 분석/이행·종료·오류 보고를 먼저 확인한다. 지원 못 하는 필수 흐름은 해결 과제로 남기며 임의로 범위 제외하지 않는다.
2. P1: ARC-YEAR/META/VERSION/SEC/PATH 실패 사례부터 작성해 수동 카탈로그·권한을 구현한다. 기존 인증·응답 DTO·세션 격리 회귀도 검증한다.
3. P2: ARC-SCAN/ORIGINAL/MANUAL/MEDIA 실패 사례→worker/후보 반영→ARC-E2E-01/02. 원본 불변·권한은 기능보다 먼저 통과해야 한다.
4. P3: UE-ANALYZE/PLAN/COPY/RECOVER/EXEC 실패·경쟁 사례→엔진 어댑터→실제 UE 검증→ARC-E2E-03/04와 성능·복구·대표 과제 5개. **이 단계 완료 전에는 사용자 요청의 1차 제품 완성으로 보고하지 않는다.**
5. P4 선택 기능은 채택한 것만 활성화한다. 폴더 열기는 실제 Windows 검증을 거쳐야 하며 브라우저 mock 성공으로 대체하지 않는다.

해당 단계의 B0/B1은 모두 통과해야 하며 blocked/미실행을 통과로 계산하지 않는다. 실제 엔진·SMB가 없으면 환경 차단으로 기록한다. 미채택 선택 기능은 분모에서 제외하되 UE 자동화는 필수이므로 제외할 수 없다. ANF 수치는 제안값임을 표시하고 팀과 확정한 목표로 최종 판정한다.

## 26 결과 기록·이번 갱신 검증 상태

기존 11장의 기록에 `ARC/UE ID, SDD 요구 ID, fixture/snapshot, 원본/대상 ID, engine build·plugins·adapter, source fingerprint, plan/manifest hash, jobId, 실제 검증 범위, 전후 파일 대조, 미해결·복구 상태`를 추가한다. UI 화면만이 아니라 API·DB·파일·엔진 보고서 증거를 연결한다.

2026-10-17 현재 모든 신규 ARC/UE 사례는 **목표·미실행**이다. 수행한 것은 현행 코드·문서 확인, 사용자 질의/답변 반영, 신규 설계·추적표 작성 및 문서 구조/상대 링크/요구 ID 정합성 점검이다. 코드·의존성·DB·원본 파일은 변경하지 않았으며 테스트 runner 설치·자동 테스트·실제 UE/SMB 실행·배포는 수행하지 않았다. 후속 답변으로 기준이 바뀌면 SDD 결정 기록과 해당 fixture·기대 결과를 함께 수정한다.
